# Current state and next steps

This file records implementation status; the complete requirements remain in the master architecture documents.

## Implemented

- React/Vite frontend with responsive home, book catalogue, multilingual search across localized titles and descriptions, author, category, and book language, category, language, and free/paid price filters, and title/author sorting. The homepage and localized category pages use filtered server-side pagination (24 books per request, up to 48) for catalogue search, ISBN, category, language, and sorting, with a browser sample-catalogue fallback if the API is unavailable. ISBN-10/13 values are checksum-validated on author drafts and admin catalogue edits, shown on public book details and Book structured data, and included in catalogue search. INR prices use one locale-aware formatter on public book cards, book details, and admin review; admin catalogue edits and author draft prices accept only values representable as whole paise, using the shared exact rupee-to-paise converter. Recent search history is stored in browser-local storage, shown as suggestions, and can be cleared; matching catalogue book title/author suggestions link directly to book details. Optional popular search trends require explicit browser-local opt-in: only terms matching a catalogue book, author, category, or language are counted, counts are not linked to accounts or stored with IP addresses, expire after 90 days, and are shown only after at least three searches. Admins can write localized descriptions for book categories; public, localized category pages show those descriptions and list active-category books, link from the homepage filters, and set client-side canonical/social metadata.
- Gujarati, Hindi, and English interface translations.
- Express/Mongoose API with MongoDB Atlas configuration, health endpoint, book catalogue endpoints, and repeatable sample-book seed command.
- Reader registration, email verification, login, logout, seven-day server-side sessions, profile editing, and password changes. Passwords use Argon2id; sessions use random HttpOnly cookies. Readers can view their active sessions and revoke any one session, including the current device; the interface stores and displays no device fingerprint or IP address.
- Transactional email adapter for Resend using server-only RESEND_API_KEY, a verified EMAIL_FROM, and an explicit public APP_BASE_URL. Verification and password-reset links expire after 30 minutes; tokens are stored as hashes and are single-use.
- Registration and password-reset email links work only when all email configuration is present. Without email configuration, development keeps its manual verification/reset-token flow. Production registration and reset remain disabled until email delivery is configured.
- Readers can request a new verification email without revealing whether an email belongs to a pending account. Login and authentication endpoints are rate-limited.
- Signed-in readers can update display name, bio, up to 10 hobbies, and an HTTPS profile-photo URL. They can also upload a private JPEG, PNG, or WebP profile photo up to 5 MB; the API validates the file signature, requires a clean ClamAV scan, and stores the image in private Cloudflare R2. The authenticated photo endpoint uses no-store and nosniff headers; private object keys are never returned. Password changes and resets revoke existing sessions.
- Signed-in readers and authors can permanently delete their account after re-entering the current password and typing `DELETE`. The workflow removes account-owned private profiles, author drafts and manuscript files, reader activity, bookmarks, wishlist, reviews, follows, sessions, and reset/verification tokens. Admin deletion is blocked. Paid-book entitlements are revoked. If any order exists, the User record remains only as a non-login tombstone with a synthetic email and anonymized name so immutable order/payment records remain valid; those financial records are not modified. Accounts with no order history are removed. Private object deletion must succeed before the database transaction, and retries are safe because object deletion is idempotent.
- Signed-in readers can download an account-data JSON export containing their profile, wishlist, author follows, reviews and helpful votes, author application/profile, draft metadata, private chapter text, reading history, and reader-owned page bookmarks. Exports exclude passwords, sessions, reset/verification tokens, MFA secrets, browser-only preferences, and uploaded file bytes; the endpoint is authenticated, rate-limited, and sent with no-store headers.
- Guest wishlists are browser-local. Signed-in readers can sync saved catalogue books to an account-owned MongoDB wishlist.
- Signed-in readers have a private library at `/library`, with separately paginated free and purchased eBooks. `GET /api/v1/reader/library` returns only books whose current free or paid access passes the internal resolver; `GET /api/v1/reader/library/:bookId` returns one safe catalogue summary only after the same access check. The multilingual `/read/:bookId` page embeds the authenticated PDF stream route and provides a direct browser-open option. Opening a book records a private per-reader last-opened timestamp after access and file checks; the library shows that timestamp, and the account-data export includes reading history. A private, no-store `GET /api/v1/reader/library/recent` endpoint supplies the eight most recently opened books, rechecking each book’s access before showing it in the localized “Continue reading” section. A signed-in reader can clear only their own reading-history records with `DELETE /api/v1/reader/library/recent`; book access and order records are unchanged. Readers can save one private PDF page bookmark per accessible book with an optional note; the bookmark endpoint rechecks access, data is reader-scoped and included in account export, and the PDF can reopen at the saved page. The embedded browser viewer does not report live page position, so readers enter bookmark page numbers manually; bookmarks are not automatic reading progress. Each library book card shows its owner's saved page and optional note, and its read link opens that page. Reading-history timestamps remain separate from page-level progress. Book details checks the signed-in reader’s access and offers a read button only when access is confirmed; a zero-price book prompts a guest to sign in, and unavailable paid purchases stay clearly disabled. Reader responses use no-store caching and omit storage keys and payment references. Since publication remains disabled and no catalogue writer links an approved manuscript as its reading source, the library will remain empty for newly submitted author books until rights/publication decisions are complete.
- Public home, book-detail, author-profile, CMS-page, and blog-post routes update localized page titles/descriptions, canonical/Open Graph/Twitter metadata, and relevant WebSite, Book, ProfilePage, CollectionPage, WebPage, or BlogPosting JSON-LD in the client. The frontend adds a `noindex` meta directive on auth, account, private workspaces, unknown routes and test checkout previews. When `SERVE_BUILT_FRONTEND=true`, Express serves the built frontend with shareable titles, descriptions and canonical links already in the HTML. Set `APP_BASE_URL` to the public origin, run `npm run build`, then start the API with this flag. Keep the built `client/dist` directory alongside the server. Private routes and checkout previews receive `X-Robots-Tag: noindex`. the API serves `/sitemap.xml` and `/robots.txt`, and Vite forwards both routes. On production, forward those two exact paths on the public frontend origin to the API. Sitemap links use `APP_BASE_URL` and include only public catalogue books, active categories and author profiles, and published blog/CMS pages.
- Book detail pages show deterministic, rule-based related-book recommendations from the public catalogue. Category, author, and language matches are scored; no reader history or private author drafts are used. The API endpoint is `GET /api/v1/books/:bookId/related`, and the client falls back to the bundled sample catalogue when the API is unavailable in development.
- Readers can write one 1–5 star review per catalogue book, edit/delete their own review, mark other visible reviews helpful once per account (and undo that vote), report reviews, and follow/unfollow catalogue authors. Helpful votes require a signed-in reader, are stored with a unique review/account constraint, and never expose voter identities. Public review summaries omit reader email and credentials. A review shows a localized verified-purchase badge only when its author has a private paid-book entitlement; no reader, order, or payment identifier is exposed.
- Admin-only review moderation routes and page can list reports, resolve them, and hide/restore reviews.
- Phase 7 commerce groundwork now includes provider-neutral Mongoose models for one-book INR orders and verified payment events. Orders snapshot the book title, author, and whole-paise amount, use a hashed per-reader idempotency key, and keep provider payment references private. Buyer/book/price snapshot fields are immutable after creation; order states can change only through validated lifecycle transitions, never direct or query-based status updates. A pending order can become paid only through a transition that records a valid provider and private payment reference. Payment event IDs are unique per provider; verified provider facts (event/order IDs, amount, currency, and verification time) are immutable, provider payment references are private, and raw webhook bodies are not stored. Catalogue sale eligibility is private and defaults to unavailable. A guarded internal service can snapshot an itemized test-mode quote for a pending one-book order from an explicitly sale-enabled catalogue item, with exact paise conversion and hashed idempotency; no HTTP order/checkout API, live payment settlement, public refund workflow, or paid access is active. A second signature-verified capture for an already-paid order is recorded as a duplicate and queued as a private, idempotent refund request; an injected test-mode adapter can simulate submission, but no refund provider worker or route is exposed. An internal-only provider-neutral event recorder accepts the original webhook bytes only in memory, requires an injected verifier to return signature-verified normalized facts, stores no raw body or signature, treats only normalized captured events as actionable, and rejects conflicting replays of the same provider event ID. The Razorpay webhook endpoint accepts only signed provider notifications, requires a server-only webhook secret, and fails closed when it is not configured; no order or checkout route is exposed. An internal processor passes only persisted captured events into the payment-application transaction; ignored events do not open a transaction, and the provider adapter remains required. A transaction-required internal service can apply only a persisted, applied, signature-verified `payment.captured` event to its matching provider payment attempt and pending one-book order, after loading the exact payment attempt ID persisted by the signature-verified webhook and checking its trusted gateway order reference, order, provider, INR currency, and exact paise amount. The first valid capture attaches the private gateway payment ID through a guarded model method; repeated matching captures are idempotent. The webhook processor posts the order's persisted, itemized author/platform/referral/tax/gateway allocation and records the buyer’s private book entitlement in the same transaction as the first successful capture. A repeated notification for the same payment skips both writes. The MFA-protected Admin Orders page checks completed refunds against the original order's amounts and flags paid orders with missing payment journal entries, missing per-order reading entitlements, or inconsistent links. It does not backfill records. Older paid orders flagged here require separate reconciliation. Paid reader access remains disabled. A separate append-only ledger transaction model validates balanced debit/credit entries in whole paise, uses a unique hashed source key for idempotency, and has no update timestamp. An internal service can post only signature-verified, applied payment events; retries are idempotent, conflicting payloads fail, and the writer loads the persisted payment event and order itself, accepts only applied events, and requires a paid INR order with a matching whole-paise amount before posting. There is no public ledger endpoint. The test-mode commission, referral allocation, GST fixture, and gateway fee are snapshotted on each order; live tax and invoice rules remain undecided. Catalogue and author-draft prices are validated to two decimal rupee places before saving, and convert exactly to integer paise.
- A private, internal-only single-book entitlement model records the reader, catalogue book, paid order, and source ledger transaction as immutable facts, with unique order and reader/book constraints. Its grant service requires a paid INR order, a matching balanced `order_payment` ledger entry, and the ledger-referenced persisted signature-verified applied payment event before issuing access, refuses unpaid or mismatched records, and treats retries as idempotent. An authenticated, rate-limited `GET /api/v1/books/:bookId/read` route now streams only an explicitly linked, approved, virus-scanned PDF after the access resolver verifies the signed-in reader’s free or purchased access. It sends private no-store/security headers and never returns a storage key. The reader access service is covered by tests: an approved linked ₹0 book grants free access without entitlement or order lookups, while paid reading requires a matching INR entitlement and valid paid order. There is still no publication path that sets the catalogue reading-source link, so real author-submitted books remain unavailable until publication rights are approved. Refund revocation and public paid checkout are still unimplemented and gated on the launch decisions.
- The provider-neutral payment-attempt model has a validated lifecycle (`created` → `pending`/`authorized` → `captured`, failure/cancellation, and refund states), integer-paise INR amounts, per-order idempotency, and private gateway references. It rejects invalid state jumps, direct document status edits, and query-based mutations that bypass the transition method; each state change must be saved before another transition. It does not store card credentials. Razorpay is selected. A server-only test-mode client creates gateway orders using the persisted local order amount, a deterministic unique receipt, and test credentials; the service checks reader ownership before contacting the gateway; receipt lookup recovers a provider response lost during retries. Provider order references are private and can only be attached through a validated payment-attempt method. An internal test checkout service creates the local order and payment attempt together, then prepares the Razorpay test order after the local transaction commits. CI exercises the flow and reuses the same attempt on retry. No HTTP order or checkout route is exposed. An internal transaction-required service creates an initial attempt only for the owning reader's pending order, snapshots the authoritative whole-paise amount, hashes idempotency keys, replays matching requests, and blocks a second live attempt.
- MFA-enabled admins can inspect a paginated, read-only financial ledger journal. The API omits source event identifiers and idempotency hashes, does not permit edits, and sends no-store responses. The ledger records the itemized test-mode commission, referral, tax, and gateway fee allocation.
- The MFA-protected admin dashboard shows aggregate account/workflow counts and safe setup readiness for database, email, MFA, R2, ClamAV, Razorpay test API credentials, and the Razorpay webhook secret. Secret values are never returned, and reader checkout remains disabled. Readiness does not reveal secret values. It checks the configured ClamAV daemon with a bounded PING request. An admin can manually request a bounded, read-only Cloudflare R2 `HeadBucket` check and a Razorpay test-key `GET /v1/orders?count=1` credential check; neither request is made automatically, and the Razorpay response is reduced to a boolean before leaving the API. Email delivery is not probed.
- The admin dashboard shows aggregate counts for active accounts, readers, authors, catalogue books, pending author applications, pending book reviews, and pending review reports. These counts are available only to authenticated admins with MFA enabled.
- The MFA-protected Admin Security page shows hourly login success/failure totals for the past 24 hours. Metrics contain no email, IP address, or account identifier, are retained for 90 days with a TTL index, and recording is best-effort so metric storage failures never change the login response. The admin endpoint is rate-limited and returns no-store responses.
- MFA-enabled administrators can review paginated, read-only history of successful admin write actions. Events retain the internal admin ID, HTTP method, sanitized route template, success status, and timestamp; request bodies, query values, and IP addresses are excluded. The history API is admin-only and returns no-store responses.
- Administrator accounts enroll in TOTP MFA after password login. TOTP secrets are encrypted with a server-only 32-byte key; recovery codes are hashed and consumed once. All admin API and page routes require an enabled MFA record. The MFA-protected security page lists up to 50 recent sessions for active administrator accounts and marks the current session; it shows internal admin ID and display name, without collecting device fingerprints or IP addresses.
- Admins can search and filter user accounts by name, email, role, and status. The user list exposes only basic account fields; admins can suspend or restore verified reader/author accounts, and suspension revokes all of that user's active sessions. Admin accounts, the current admin, and unverified accounts cannot be changed from this page.
- Admins can search author storefronts and view follower, public-catalogue, draft, and submitted-book totals. They can suspend/restore author profiles; suspension hides the public storefront and blocks author-only API routes while preserving the account. A suspended user account must be restored before its author profile can be restored.
- Admins can search existing public catalogue entries and edit localized titles and descriptions, language, category, badge, and card theme. The catalogue editor displays the stored price read-only. Metadata updates must match the current price and cannot replace it. The original catalogue author credit and book ID remain fixed. This does not publish author drafts or enable purchases.
- Admins can select up to four existing public-catalogue books for a homepage featured-books widget; this does not publish author drafts or enable sales. Admins can configure maintenance mode, which serves a localized notice to public visitors and returns 503 for public API actions while keeping protected admin routes available; the mode is off by default. Admins can choose the default language for new visitors (saved visitor preferences take priority), manage localized homepage search titles and descriptions, edit the localized homepage hero, reorder and show or hide built-in sections (book discovery stays visible), add up to four localized custom text sections with optional same-site links and published media-library images, manage localized header links, footer copy, browse links, and the community column title and links, and turn an optional announcement banner on or off. Site links are restricted to same-site paths or page anchors.
- Admins can add and localize categories in Gujarati, Hindi, and English, change display order, and disable unused categories. Categories with catalogue books or author drafts cannot be disabled. Reader filters, author drafts, and catalogue editing use the active database categories.

- Admins can create, edit, and publish/unpublish static CMS pages and blog articles with Gujarati, Hindi, and English text. - Approved authors can update their public biography, HTTPS website link, profile photo URL, and storefront cover image URL. They can feature up to three books from their existing public catalogue. Author-owned routes enforce author role and ownership; admin review routes require admin access.

Admins can configure whole-megabyte limits for new cover uploads from 1–10 MB (default 5 MB) and manuscripts from 1–25 MB (default 25 MB); server and author UI enforce the saved limits, while the upload parser retains a 25 MB hard ceiling. ## Phase 7 launch decisions

- The owner selected digital eBooks sold as separate one-time book purchases for the initial release. Print-on-demand and monthly reader membership are deferred.
- Razorpay is the selected payment provider. The backend has test-mode order creation, checkout-signature verification, and webhook verification. Checkout signatures are matched against the server-stored order and reader-owned attempt; signature verification alone does not mark an order paid. No Razorpay API keys are committed; server secrets must be configured outside source control. Public order creation and reader checkout remain unavailable. The author/platform/referral split is now approved for the test model; live GST rate, invoice issuer, refund policy, and author-rights wording remain subject to review.
- Checkout and paid access stay disabled. Test pricing is implemented; live GST/invoice details, refund policy, and author-rights wording still require review and owner approval. Razorpay is the selected test-mode provider.

- An internal reading access check requires a catalogue book linked to an approved, scanned PDF source with a matching approved price. Reading requires a signed-in account. A linked ₹0 book needs no payment. A priced book requires the reader’s matching entitlement and an order in the paid state. The check returns an internal source ID and never returns the storage key. No publication path sets the source link. The authenticated read-stream route is implemented, but no catalogue entry can yet be linked to an approved source, so it cannot serve a public book.

## ત્રણેય પેનલની ટેસ્ટ ચકાસણી

1. GitHub Codespaceમાં નવીનતમ `main` પર `npm install` અને `npm run dev:all` ચલાવો. **Ports** માંથી 5173નું **Open in Browser** પસંદ કરો. સાઇટમાં બધા પાથ એ જ સરનામા પરથી ખોલો.
2. **રીડર · `/reader/login`**. વેરિફાઇડ રીડર તરીકે લૉગિન કરો. નીચેની Phase 7 સૂચના પ્રમાણે ₹100ની અને મફત બુક ખોલો. ₹100ની બુકમાંથી રેફરલ લિંક બનાવો, પછી બીજા બ્રાઉઝર સેશનમાં અલગ રીડર તરીકે લૉગિન કરીને એ લિંક ખોલો. ટેસ્ટ ચેકઆઉટ સુધી લિંકમાં રેફરલ કોડ અને ₹139.29 બંને જળવાવાં જોઈએ.
3. **લેખક · `/author/login`**. સક્રિય લેખક પ્રોફાઇલથી લૉગિન કરો અને `/author/books` ખોલો. ટેસ્ટ ડ્રાફ્ટમાં શીર્ષક, વર્ણન અને ₹100 ભાવ ભરો. JPEG, PNG અથવા WebP કવર અને PDF અપલોડ કરો. બંને ફાઇલ પાસે સ્કેન સફળ બતાવ્યા પછી ડ્રાફ્ટ સમીક્ષા માટે મોકલો.
4. **એડમિન · `/admin/login`**. MFA ધરાવતા ટેસ્ટ એડમિન તરીકે લૉગિન કરો. `/admin/author-books` ખોલીને એ જ ડ્રાફ્ટ અને ₹100 ભાવ ચકાસો, પછી મંજૂર કરો. રીડરના કેટલોગમાં તે ખાનગી ડ્રાફ્ટ શોધો. પ્રકાશનની મંજૂરી બાકી હોવાથી તે દેખાવું જોઈએ નહીં.

ફાઇલ અપલોડ પહેલાં એડમિન ડૅશબોર્ડમાં ClamAV અને ખાનગી Cloudflare R2ની સ્થિતિ ચકાસો. જરૂરી સર્વર સેટિંગ અને પ્રથમ એડમિન બનાવવાની રીત [README](../../README.md)માં છે. ચકાસણી માટે અલગ ટેસ્ટ ડેટાબેઝ અને ખાનગી ટેસ્ટ બકેટ વાપરો.

ખાનગી ટેસ્ટ બકેટ અને ClamAV ગોઠવ્યા પછી, એક નમૂનાની ફાઇલ સ્કેન કરવા અને R2માં લખી, વાંચી અને દૂર કરીને ચકાસવા માટે પ્રોજેક્ટના મૂળ ફોલ્ડરથી આ કમાન્ડ ચલાવો.

```sh
npm run verify:storage --workspace @rasbhav/server -- --test-bucket
```

આ કમાન્ડ માટે ટેસ્ટ બકેટમાં લખવા, વાંચવા અને દૂર કરવાની પરવાનગી જોઈએ. કમાન્ડ સફળ થાય પછી લેખક પેનલમાં કવર અને PDF અપલોડથી શરૂ થતી આખી પ્રક્રિયા ચકાસો.

GitHub CIમાં Chromium સાથે રીડરનો ટેસ્ટ ચેકઆઉટ અને રેફરલ, લેખકની ખાનગી રજૂઆત, તેમજ MFA પછી એડમિનની મંજૂરી ચકાસાય છે. અપલોડ ટેસ્ટ નમૂનાના સ્કેનરથી નકારાયેલી ફાઇલ અને સ્ટોરેજ વગર અટકતી ફાઇલ ચકાસે છે. વાસ્તવિક ClamAV અને R2 સાથે સફળ અપલોડ માટે ઉપરનું ત્રીજું પગલું ચલાવવું જરૂરી છે.

The MFA-protected Admin Orders page shows counts and INR totals across paid, refund-pending and fully refunded orders. The summary covers all pages regardless of the active table filter and counts each local order once.

The private Author Studio includes the author share on paid orders after catalogue entries are linked to approved, scanned source manuscripts. An order snapshots the beneficiary from that link. Older unlinked orders are excluded from author reports; buyers and beneficiary IDs are not exposed. Full refunds remove the share from the author total.

## Phase 7 ચકાસવાની રીત

ટેસ્ટ ડેટાબેઝ સાથે પ્રોજેક્ટના મૂળ ફોલ્ડરમાં નીચેનો કમાન્ડ ચલાવો.

```sh
npm run seed:books --workspace @rasbhav/server -- --review-fixtures
```

પછી સાઇટમાં `/books/phase7-review-paid` અને `/books/phase7-review-free` ખોલો. આ નમૂના કેટલોગમાં કિંમત ચકાસવા માટે છે.

1. ટેસ્ટ દર GST 5% અને ગેટવે ફી 2% હોય ત્યારે કેટલોગમાં લેખકભાવ ₹100 ધરાવતી બુક ખોલો. કિંમતની વિગતો ખોલતાં કુલ ₹139.29, GST ₹6.50 અને ગેટવે ફી ₹2.79 દેખાવી જોઈએ.
2. **ટેસ્ટ ચેકઆઉટ** ખોલો. પુસ્તકનું નામ અને અંતિમ કિંમત સરખાવો. આ પ્રિવ્યૂ પૈસા વસૂલતું નથી. મફત બુક માટે કિંમત ₹0 હોય છે.
3. [MongoDB ટેસ્ટ](../../server/integration/razorpay-capture.mjs) સીધી ખરીદીમાં લેખકના ₹100 અને પ્લેટફોર્મના ₹30 તપાસે છે. રેફરલવાળી ખરીદીમાં પ્લેટફોર્મના ₹20 અને રીડરના ₹10 તપાસે છે.
4. એ જ ટેસ્ટમાં વધારાની ચુકવણી પરત કર્યા પછી એક વેચાણ અને વાંચન-પ્રવેશ જળવાય છે. મૂળ ખરીદીના સંપૂર્ણ રિફંડની પુષ્ટિનું અનુકરણ કરતાં વેચાણના હિસ્સા રદ થાય છે અને એ ખરીદીથી મળતો વાંચન-પ્રવેશ બંધ થાય છે.

## Phase 7 test pricing model

- Owner-approved test split: author price is the author share; add a 30% platform commission on that author price. For a valid referral, allocate 10% of the author price from the platform commission to the referring reader, leaving 20% for Rasbhav Books. The buyer total is the same for direct and referred sales.
- Test fixture defaults are illustrative only: GST 5% (`TEST_GST_RATE_BPS=500`) and Razorpay processing 2% (`TEST_GATEWAY_RATE_BPS=200`). Both rates can be changed in environment configuration for tests. The test GST is applied to the author price plus platform commission. Gateway cost is calculated on the final buyer total, including that fee, using whole-paise rounding.
- The catalogue API and book cards/details show the computed test total. Pending order snapshots retain the amounts, rates, and referral beneficiary used for that quote. No public checkout endpoint is exposed, no live payment can be accepted, and the current illustrative rates must not be used for live tax or invoices.
- ₹100 test example at 5% GST and 2% gateway: direct purchase total ₹139.29 (author ₹100, Rasbhav Books ₹30, GST ₹6.50, gateway ₹2.79); valid referral has the same total (author ₹100, Rasbhav Books ₹20, referrer ₹10, GST ₹6.50, gateway ₹2.79). Test-only refund planning models refunding the second captured payment while keeping the original order paid, and full refund reversals including the relevant shares. Duplicate capture webhooks create an idempotent private refund request; test-only submission requires an injected provider. An internal test-only service applies a completed full refund confirmation for the original payment, moving the order and its original payment attempt to refunded and posting one reversal atomically. A pending refund preserves existing reading access and referral attribution. Both end when the full refund completes. No live refund provider call or public refund route is active. Gateway fee is assumed to remain as a cost after refund in this fixture.
- A free approved book remains ₹0 and can be read without checkout or payment entitlement. Free books never pass through the paid-order service.
- Refund policy and author publication-rights terms are review drafts, not active terms. Publishing and live checkout stay off pending legal review and owner approval. Live GST rate and the invoice issuing party remain undecided.

Provider-neutral persistence models now cover one-book order snapshots, payment attempts, verified payment events, and balanced append-only ledger transactions; validation tests cover integer-paise amounts, idempotency, balanced entries, and payment state transitions. A paginated, authenticated, no-store reader order-history API and Gujarati/Hindi/English account view now expose only sanitized records owned by the signed-in reader. MFA admins can inspect the read-only sanitized ledger journal, a read-only payment-event reconciliation view, and a paginated order list filtered by lifecycle status. The order list omits reader identity, idempotency hashes, and gateway payment references. Keep checkout and paid access disabled until legal and live tax/invoice details are reviewed and approved; keep public publishing of author drafts disabled until the author-rights wording is legally reviewed and approved. Phase 5 file uploads remain unavailable until a private Cloudflare R2 bucket and reachable ClamAV daemon are configured. Configure `ADMIN_MFA_ENCRYPTION_KEY` before administrator access, and configure email secrets plus the public frontend URL before enabling production registration or password reset.
